# גל 0 — תוצאות אפליקציית הבדיקה `over-probe`

נמדד 3.9.2026 על Postgres של xhostd, דרך אפליקציית `app` זמנית שהריצה `psql`
ב-`launch.sh` והדפיסה ללוג. שתי הרצות (deploy `012475f5`, deploy `989560d4`).
האפליקציה נמחקה בסיום. כל שורה כאן היא פלט, לא הנחה.

---

## 1. PostGIS — **קיים**. החסם של v1 נפל

```
create extension if not exists postgis schema extensions;   →  CREATE EXTENSION
postgis_full_version() →
  POSTGIS="3.6.4 94d984b" [EXTENSION] PGSQL="180"
  GEOS="3.14.1-CAPI-1.20.5"  PROJ="9.8.1"  LIBXML="2.9.14" LIBJSON="0.18"
  LIBPROTOBUF="1.5.1" WAGYU="0.5.0"
```

**3.6.4 — חדש יותר מ-Neon (3.6.0).** נוספו גם `postgis_raster`, `postgis_topology`,
`postgis_sfcgal`, `postgis_tiger_geocoder`, `address_standardizer`.
סך ה-extensions הזמינות: **60** (מול 46 שנמדדו ב-1.9 — הפלטפורמה הוסיפה אותן מאז).

מה שנבדק בפועל, ולא רק ההתקנה:

| בדיקה | תוצאה |
|---|---|
| `extensions.geometry(Point,4326)` כעמודה | ✅ |
| `ST_SetSRID(ST_MakePoint(...))` + `INSERT` | ✅ |
| אינדקס `USING gist (g)` | ✅ |
| `ST_AsText` **מתפקיד הקריאה-בלבד** | ✅ `POINT(34.78 32.08)` |
| `extensions.spatial_ref_sys` מתפקיד הקריאה-בלבד | ✅ **8,500 שורות** |
| `ST_Transform` מ-EPSG:2039 (ITM) ל-4326, מתפקיד הקריאה-בלבד | ✅ `POINT(34.76544131012447 32.059494833471156)` |

השורות האחרונות חשובות: בהרצה הראשונה `GRANT SELECT ... IN SCHEMA extensions` הוציא
`WARNING: no privileges were granted for "spatial_ref_sys"` (אנחנו לא הבעלים).
זה **לא** חוסם — PostGIS נותן `PUBLIC` הרשאת קריאה על הטבלה בעצמו. בלי הבדיקה הזו
היינו יכולים להסיק בטעות ש-`ST_Transform` שבור בקונסולה הציבורית.

## 2. הרשאות התפקיד המוזרק

| פעולה | תוצאה |
|---|---|
| `CREATE SCHEMA` | ✅ |
| `CREATE EXTENSION` (מתוך ה-60) | ✅ |
| `CREATE EXTENSION postgres_fdw` | ❌ `Must be superuser` |
| `CREATE ROLE` | ❌ `permission denied to create role` |
| `CREATE DATABASE` | ❌ `permission denied to create database` |
| `SET session_replication_role = replica` | ❌ `permission denied to set parameter` |
| `rolsuper / rolcreaterole / rolcreatedb / rolbypassrls` | כולם `f` |

התפקיד: `r_<channel_id>`; המסד: `ch_<channel_id>`.

**מסקנות תפעוליות:**
* `CREATE DATABASE` חסום → **אפליקציה אחת = מסד אחד**. שני מסדים = שתי אפליקציות. הטופולוגיה ב-v2 §3 מאושרת.
* `session_replication_role` חסום → הסבבים החוזרים ב-`pg_resync_data.py` להתרת FK **עדיין נדרשים**.
* `postgres_fdw` חסום → מתיישב עם התוכנית למחוק את `ocal_srv` (0 foreign tables ממילא).
* `CREATE ROLE` חסום, **וזה כבר לא משנה** — ראה §3.

## 3. תפקיד הקריאה-בלבד המוזרק — עונה על הכרעה 2

`DATABASE_URL_READONLY` מוזרק לכל ערוץ. התפקיד: `r_<channel_id>_ro`.

| בדיקה | תוצאה |
|---|---|
| `SELECT` על טבלה ב-`public` שנוצרה **אחרי** ה-GRANT | ✅ — הכיסוי על `public` אוטומטי |
| `GRANT USAGE/SELECT` על סכימה שאינה `public` | ✅ |
| `ALTER DEFAULT PRIVILEGES ... GRANT SELECT` | ✅ |
| `SELECT` על סכימה **בלי** GRANT | ❌ `permission denied for schema secret_s` |
| `CREATE TABLE` | ❌ `permission denied for schema` |
| `INSERT` | ❌ `permission denied for table` |
| `SELECT` מ-`pg_catalog.pg_authid` | ❌ `permission denied for table pg_authid` |
| `SELECT` מ-`pg_stat_activity` | ✅ |

זו הראיה שהופכת את **א׳-הפוכה** (v2 §3) לנכונה: הקונסולות הציבוריות יכולות לרוץ על
תפקיד שהפלטפורמה מתחזקת, בלי `CREATE ROLE`, ו-Postgres עצמו מסרב לכתיבה. הנסיגה
האבטחתית ש-v1 חשש ממנה **לא מתרחשת**.

⚠️ ההיפוך של אותה עובדה: הכיסוי על `public` הוא **אוטומטי ובלתי ניתן לביטול בקלות**.
כל טבלה ב-`public` של מסד האפליקציה קריאה לתפקיד הזה. לכן טבלאות ה-auth של OVER
(`api_users`, `users`) לא יכולות לשבת באותו מסד — בדיוק כפי ש-v2 קבע כשמחק את דרך ב׳.

## 4. הגדרות Postgres של xhostd

```
server_version                    18.4 (Debian 18.4-1.pgdg13+1)     ← המקור ב-Neon: 18.6
shared_buffers                    1 GB
effective_cache_size              3 GB
work_mem                          8 MB
maintenance_work_mem              256 MB
max_connections                   500
max_worker_processes              16
max_parallel_workers_per_gather   2
max_wal_size                      1 GB
statement_timeout                 0
```

**כולם ניתנים לשינוי ברמת session** — נבדק: `work_mem`→256MB, `maintenance_work_mem`→1GB,
`max_parallel_workers_per_gather`→4, `statement_timeout`→10s, וגם **מתפקיד הקריאה-בלבד**.
שתי השלכות:
* הקונסולה הציבורית יכולה להרים `work_mem` לשאילתה כבדה במקום להיחנק על 8 MB.
* אפליקציית הטעינה (גל 7) יכולה להרים `maintenance_work_mem` לבניית האינדקסים.

⚠️ `max_wal_size` הוא 1 GB בלבד ואינו ניתן לשינוי ב-session. בטעינה של 58 GB זה אומר
checkpoint-ים תכופים. זה גורם תפוקה שיש למדוד בגל 5, לא לנחש.

## 5. סביבת ההרצה — שלוש הפתעות

```
base image      xhost-runtime:node22-py313      ← Python 3.13, Node 22
XHOST_HTTP_PORT 3000
image           994.78 MB total, 46.13 MB charged (base exempt)
psql מ-apt של Debian trixie:  17.11             ← לא 18
```

1. **Python 3.13 / Node 22.** ב-Render: `PYTHON_VERSION=3.11`, `NODE_VERSION=20`.
   מעבר ל-xhostd הוא גם שדרוג runtime שלא נבחר. חייב אימות בגל 1/2.
2. **`psql`/`pg_dump` מ-Debian הם 17.11**, והמקור הוא 18.6. `pg_dump` 17 **יסרב** לדמפ
   שרת 18. דרישת ה-PGDG ב-v2 §9 מאושרת — לא ניתן לוותר עליה.
3. **הבסיס פטור מתקרת ה-image.** 994 MB נספרו כ-46 MB.

## 6. משתני הסביבה המוזרקים — מאשר את §5 פריט 11ב

השמות שהוזרקו לקונטיינר (ערכים ממוסכים):

```
DATABASE_URL   DATABASE_URL_READONLY   PORT   XHOST_HTTP_PORT
XHOST_FORWARD_PORT   XHOST_READY_FILE
S3_ACCESS_KEY_ID   S3_BUCKET   S3_ENDPOINT   S3_REGION   S3_SECRET_ACCESS_KEY
HOME HOSTNAME NODE_VERSION PATH PWD UV_CACHE_DIR XDG_CACHE_HOME YARN_VERSION npm_config_cache
```

ותיעוד `set_env` מונה את השמורים במפורש:
`XHOST_USER, XHOST_SHA, XHOST_HTTP_PORT, PORT, XHOST_FORWARD_PORT, XHOST_READY_FILE,`
`DATABASE_URL, DATABASE_HOST, DATABASE_PASSWORD, S3_ENDPOINT, S3_BUCKET,`
`S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY, S3_REGION`.

**ההצלבה מול `app/config.py`:**

| OVER קורא | ב-xhostd | תוצאה בלי תיקון |
|---|---|---|
| `S3_ENDPOINT` | **שמור + מוזרק** | מצביע ל-Blob של xhostd |
| `S3_BUCKET` | **שמור + מוזרק** | דלי של xhostd |
| `S3_REGION` | **שמור + מוזרק** | אזור של xhostd |
| `S3_ACCESS_KEY` | פנוי | מפתח R2 שלנו |
| `S3_SECRET_KEY` | פנוי | מפתח R2 שלנו |
| `S3_PUBLIC_BASE_URL` | פנוי | `files.over.org.il` |

כלומר OVER היה שולח **מפתחות R2 אל ה-endpoint והדלי של xhostd** — כישלון, או גרוע
מכך כתיבה ליעד הלא נכון, **בשקט**. התיקון `R2_*` בעדיפות (v2 §5 פריט 11ב) הוא חובה.
שים לב ש-`DATABASE_URL_READONLY` **אינו** ברשימת השמורים וניתן לדריסה.

## 7. תיקון לממצא של v2 — ל-worker **יש** retry, אבל הוא קצר מדי

v2 §1 כתב: "ב-`over_worker.py` בריפו GOVSCRAPER **לא נמצאה** לוגיקת retry/backoff על
5xx (grep ריק)". ה-grep רץ על `over_worker.py` שברוט הריפו — קובץ **shim בן 11 שורות**.
המימוש הוא `govscraper/legacy/over_worker.py`, **5,251 שורות**, ובו יש retry:

```
max_attempts = 3
5xx  → wait = 15 * attempt   (15s, 30s)
חריגה → wait = 10 * attempt
```

**סך הסבילות: ~45 שניות.** המסקנה של v2 עומדת אבל מסיבה אחרת: לא "אין retry" אלא
"ה-retry קצר בשני סדרי גודל מחלון תחזוקה". חלון של דקות יאבד את ההעלאה, והתוצאה
אינה נשמרת לדיסק בין ניסיונות. הפריט בגל 1 נשאר — עם המספר הזה כנקודת מוצא.
