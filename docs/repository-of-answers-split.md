# פיצול מאגר התשובות לפי "סוג מידע"

`https://www.gov.il/he/Departments/DynamicCollectors/repository-of-answers`
נעקב ב-OVER כמאגר יחיד — [82db2f91](https://www.over.org.il/versions/82db2f91-9ff0-44f4-b842-df3c43f7185a).
זהו אחד המאגרים הכבדים במערכת, והגירוד שלו נכשל לעיתים קרובות.

המסמך הזה מתעד את הפיצול שלו לחמישה מאגרים לפי הפילטר "סוג מידע" (`Info`)
שקיים בממשק של gov.il עצמו, את מה שנמדד בדרך, ואת מה שהפיצול **לא** פותר.

## למה הפיצול עובד ללא שינוי בסקרייפר

מנוע gov.il מעביר כל פרמטר query שאינו פרמטר עימוד אל תוך ה-`QueryFilters`
של ה-API — ראו את בלוק `extra_filters` ב-
`govscraper/scrapers/govil/legacy_engine.py`. כלומר `?skip=0&Info=4` באמת
מגרד רק "הסכם התקשרות". אומת מול המקור החי:

| בדיקה | תוצאה |
| --- | --- |
| `GovILScraper.scrape(...&Info=3)` | 3 פריטים — בדיוק כמו שה-API מדווח |
| `GovILScraper.scrape(...&Info=2)` | 194 פריטים — בדיוק כמו שה-API מדווח |

בצד OVER, זהות ה-URL (`app/services/url_identity.py`) שומרת על מחרוזת ה-query,
ולכן חמשת ה-URL-ים המסוננים והמאגר המקורי הם שש זהויות נפרדות. זו התכונה
שכל הפיצול עומד עליה, והיא נעולה ב-`tests/test_repository_of_answers_split.py`.

## מה יש במאגר בפועל

נמדד ב-2026-09-07 בסריקת מטא-דאטה מלאה (15,517 פריטים, ללא הורדת קבצים):

| Info | סוג מידע | פריטים | קבצים |
| ---: | --- | ---: | ---: |
| 1 | דו"ח התקשרויות | 2,191 | 2,455 |
| 2 | דוח | 194 | 164 |
| 3 | היתר | 3 | 7 |
| 4 | הסכם התקשרות | 1,726 | 1,888 |
| 5 | תשובה | 11,144 | 18,833 |
| — | **ללא סוג מידע** | **305** | **375** |
| | **סה"כ** | **15,517** | **23,673** |

השמות לקוחים מבלוק `InfoMultiChoiseValues` בדף עצמו, כדי שייקראו בדיוק כמו
הפילטר בממשק.

## שתי מגבלות שחשוב להכיר

**1. הפיצול אינו ממצה — 305 פריטים אינם נושאים `Info` כלל.** אין פילטר שמגיע
אליהם: `Info=_none` מחזיר 70 בלבד. לכן **המאגר המקורי נשאר פעיל**, בקצב נדיר
(90 יום) במקום שבועי, כרשת ביטחון שמכסה את כל 15,517 הפריטים. הוא לא מושבת
ולא נמחק.

**2. Info=5 (תשובה) נשאר כבד.** הוא 72% מהעומס — 11,144 פריטים ו-18,833
קבצים, כלומר סריקה של ~5 שעות במקום 6.5. הרווח האמיתי הוא שארבעת האחרים
הופכים קטנים ויציבים, וכישלון באחד מהם כבר לא מוחק את עבודת השאר. אם בהמשך
נרצה לחתוך גם אותו, בדף יש פילטרים `Date_from`/`Date_to` ו-`Topic` שאפשר
להעמיס על אותו מנגנון בדיוק.

בנוסף, 33 פריטים נושאים יותר מ-`Info` אחד ויופיעו בשני מאגרים. זה נסבל.

## הרצה

```bash
export OVER_ADMIN_TOKEN=eyJ...   # ה-JWT מ-localStorage.token ב-over.org.il
python scripts/split_repository_of_answers.py --dry-run
python scripts/split_repository_of_answers.py
```

יצירת מאגר בידי אדמין מסמנת אותו `active` **ומזניקה מיד גירוד ראשון**, ולכן
הרצה מלאה מתחילה חמש סריקות במקביל. אפשר לפרוס אותן:

```bash
python scripts/split_repository_of_answers.py --only 3,2,4,1
python scripts/split_repository_of_answers.py --only 5
```

הסקריפט אידמפוטנטי — מאגר שכבר קיים מדווח ומדולג, לא משוכפל.

## שינוי נלווה: PATCH על קצב סקירה

הסקריפט מאט את המאגר המקורי דרך `PATCH /api/datasets/{id}`. עד עכשיו הנתיב
הזה עדכן את `poll_interval` ב-DB אבל לא נגע ב-job של ה-scheduler, כך שהקצב
החדש נכנס לתוקף רק בדפלוי הבא (כש-`init_scheduler` קורא הכול מחדש). זה בדיוק
המקרה שבו זה מפריע — האטה של מאגר כבד אמורה לתפוס מיד — ולכן
`app/api/datasets.py` קורא עכשיו ל-`add_poll_job` כשהקצב באמת השתנה.
